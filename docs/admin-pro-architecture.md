# SLOPAY-BUKET ADMIN PRO — архитектура и план внедрения

## Статус документа

- Репозиторий: `marcostavar24633-cyber/slopay-buket`
- Базовая ветка: `main`
- Рабочая ветка: `feature/admin-pro-foundation`
- Цель: заменить небезопасную прямую работу браузера с GitHub на защищённый API Cloudflare Worker и подготовить админку к управлению актуальным сайтом из `redesign/index.html`.
- Принцип хранения: без отдельной базы данных. GitHub остаётся источником контента и истории изменений.

## 1. Фактическое состояние, подтверждённое исходниками

1. Проект использует Vite, React 18 и TypeScript.
2. `wrangler.jsonc` указывает Worker `worker.js` и статические ресурсы из `dist/`.
3. Текущий `worker.js` только передаёт запросы в `env.ASSETS.fetch(request)`; API админки на Worker пока не реализован.
4. Текущий клиентский модуль `src/admin/github.ts` обращается к GitHub API непосредственно из браузера.
5. В этом же модуле токен хранится в `localStorage` или `sessionStorage`. Это необходимо убрать до production-использования.
6. Текущий визуальный редактор `src/admin/pages/editor.tsx` загружает `editor-preview.html?edit=1`. Его протокол `postMessage` нельзя автоматически считать совместимым с `redesign/index.html`.
7. В `README.md` описана старая схема публикации через GitHub Actions и прямой токен пользователя. Её нужно актуализировать после внедрения новой архитектуры.
8. Текущая конфигурация Worker не содержит API-маршрутов, проверки сессии, ограничения запросов и собственных security headers.

## 2. Целевая архитектура

```
Браузер администратора
  |
  | HTTPS + защищённая сессия
  v
Cloudflare Access
  |
  v
Cloudflare Worker
  |-- /api/auth/*       проверка доступа и сессии
  |-- /api/content/*    чтение и запись разрешённых JSON
  |-- /api/media/*      безопасная загрузка изображений
  |-- /api/deploy/*     статус публикации и запуск разрешённого workflow
  |-- /api/health       диагностика API и конфигурации
  |
  | GitHub API, токен только в Worker Secret
  v
GitHub repository
  |-- content/*.json
  |-- public/...        медиафайлы
  |-- история коммитов
  v
CI build → проверка → публикация
  |
  v
Публичный сайт
```

### Обязательные принципы

- GitHub-токен никогда не отправляется в браузер и не включается в HTML, JS, логи или ответы API.
- Секрет GitHub задаётся в Cloudflare как Worker Secret, например `GITHUB_TOKEN`.
- Админка закрывается Cloudflare Access. Проверка только на клиенте не считается защитой.
- Worker проверяет Access identity на каждом защищённом API-запросе.
- API работает по allowlist: клиент не может передать произвольный путь GitHub API или произвольный путь файла.
- Для записи используются только заранее разрешённые JSON-файлы и каталоги медиа.
- Все изменения проходят серверную валидацию схемы и размера.
- Сохранение использует текущий blob SHA; конфликт версий возвращает HTTP 409 и требует повторного чтения.
- Никаких секретов и персональных данных клиентов в Git-коммитах и логах.
- Не создавать отдельную базу данных. GitHub JSON — источник данных каталога, контента и настроек. Заказы не должны изображаться как сохранённые, если фактически они только открывают мессенджер.

## 3. API Worker

Все API-маршруты имеют префикс `/api`.

| Метод и маршрут | Назначение | Требования |
|---|---|---|
| `GET /api/health` | Проверка работоспособности Worker | Не раскрывает секреты и внутренние значения |
| `GET /api/session` | Проверка текущей Access identity | Возвращает только безопасные сведения о сессии |
| `GET /api/content/:key` | Чтение разрешённого набора контента | `:key` только из allowlist |
| `PUT /api/content/:key` | Запись JSON-контента | Валидация схемы, лимит тела, SHA-конфликт |
| `POST /api/media` | Загрузка изображения | MIME и сигнатура файла, размер, безопасное имя |
| `GET /api/deploy/status` | Последний статус CI/deploy | Только чтение разрешённых workflow |
| `POST /api/deploy` | Запуск публикации | Только разрешённый workflow, CSRF/Origin-проверка |
| `GET /api/audit` | Последние изменения | Только метаданные коммитов, без секретов |

### Ответы и ошибки

- `200` — успешно.
- `400` — некорректный запрос или JSON.
- `401/403` — нет действующей авторизации или прав.
- `404` — неизвестный ключ/маршрут.
- `409` — файл изменился после чтения; клиент должен перечитать данные.
- `413` — превышен лимит тела/файла.
- `415` — неподдерживаемый тип файла.
- `429` — превышен лимит запросов.
- `500` — внутренняя ошибка без раскрытия stack trace и секретов.

## 4. Защита Worker

1. Проверять Access JWT по официальному публичному ключу и ожидаемым issuer/audience либо использовать подтверждённый Cloudflare Access service binding/механизм проверки. Нельзя доверять произвольному заголовку с email.
2. Разрешать только конкретные Access identity или домен/группу, заданные конфигурацией.
3. Для изменяющих запросов проверять `Origin`, `Content-Type` и CSRF-защиту.
4. Ограничить методы, маршруты, размер тела и частоту запросов.
5. Не проксировать произвольные URL, заголовки и GitHub API paths.
6. Установить CSP, HSTS, `X-Content-Type-Options: nosniff`, `Referrer-Policy` и подходящую `frame-ancestors` политику. Не ломать нужный preview iframe админки.
7. Исключить токены, тела форм и чувствительные данные из логов.
8. Проверять изображения не только по расширению и MIME, но и по сигнатуре. SVG не принимать без отдельной безопасной обработки.
9. Ввести лимиты на количество и размер загружаемых файлов.
10. Не включать публичный доступ к API записи даже при ошибке конфигурации Access.

## 6. Визуальный редактор нового сайта

- Цель редактирования: актуальный `redesign/index.html`, а не архивный `editor-preview.html`.
- До разработки составить карту реальных секций и редактируемых полей нового сайта.
- Редактор должен получать контент из тех же JSON-источников, что и публичный сайт.
- Предусмотреть предпросмотр desktop/tablet/mobile.
- Изменения сначала сохраняются как черновик в состоянии приложения; публикация выполняется отдельным действием.
- Для каждого редактируемого поля определить тип, ограничения длины, допустимый формат и обязательность.
- Не разрешать ввод произвольного HTML. Для форматированного контента использовать ограниченный набор блоков и безопасную сериализацию.
- Проверить происхождение сообщений iframe: точный `origin`, `source`, тип и схему каждого сообщения.
- Сверить фактический протокол preview с новым дизайном. Не считать старые `slopay:*` сообщения рабочими без обработчика на новой странице.

## 7. Функциональные модули

### Дашборд
- Состояние сайта и последней сборки.
- Количество товаров, видимых товаров, категорий и отзывов.
- Предупреждения по незаполненным SEO-полям, отсутствующим фото и ошибкам контента.
- Быстрые ссылки на проблемные разделы.

### Каталог
- Список, поиск, фильтры и сортировка.
- Создание, редактирование, скрытие и архивирование товара.
- Цена, состав, категория, признаки «хит» и «показывать».
- Проверка уникальности ID/slug и ссылок на изображения.

### Категории
- Название, slug, описание, порядок, SEO title/description.
- Проверка связи товаров с категориями.

### Заказы и обращения
- Показывать только реально доступные данные.
- Если сайт лишь открывает MAX/Telegram с подготовленным текстом, раздел должен честно называться «Обращения» или «Инструкции по заказу», а не выдавать переходы в мессенджер за сохранённые заказы.
- Для реального учёта заказов потребуется отдельный защищённый endpoint и согласованное хранилище/уведомление; это отдельное решение, не часть GitHub JSON-каталога.

### Медиабиблиотека
- Загрузка, просмотр, поиск и проверка использования изображения.
- Ограничения форматов и размера.
- Предпросмотр и проверка битых ссылок.
- Запрет на небезопасный SVG и исполняемые файлы.

### Страницы и блоки
- Управление текстом, изображениями, порядком и видимостью блоков.
- Проверка обязательных секций и пустых ссылок.
- Безопасные типизированные блоки вместо произвольного HTML.

### SEO
- Title, description, canonical, Open Graph.
- Проверка H1, заголовков, alt, sitemap и robots.
- Предпросмотр сниппета и список ошибок.

### Аналитика
- Отображать только подключённые и реально полученные данные.
- Не имитировать статистику, если API аналитики не подключено.
- События и цели документировать отдельно.

### Мониторинг и публикация
- Статус последней сборки, commit SHA, время и ссылка на workflow.
- Ошибки сборки и тестов.
- Публикация с подтверждением и защитой от двойного запуска.
- Откат через Git revert/выбор проверенного коммита, не перезапись истории force push.

### Настройки, безопасность и журнал
- Контакты, режим работы, доставка, мессенджеры и юридические реквизиты.
- Роли только если появятся дополнительные администраторы; иначе оставить одного Access-пользователя.
- Журналировать кто, когда и какой файл изменил, используя проверенную Access identity и commit SHA.
- Не записывать в журнал секреты или содержимое приватных сообщений.

## 8. Этапы реализации

### Этап 0 — инвентаризация и резервирование
- Зафиксировать текущую ветку main и состояние production.
- Создать отдельную feature-ветку.
- Проверить реальные схемы `content/*.json`, публичную сборку и текущие тесты.
- Не менять публичный дизайн и контент в рамках внедрения админки.

### Этап 1 — защищённый backend
- Реализовать маршрутизацию Worker.
- Подключить Cloudflare Access и серверную проверку identity.
- Настроить GitHub token secret.
- Реализовать allowlist чтения/записи контента.
- Добавить валидацию, лимиты, конфликты SHA, заголовки безопасности и тесты.
- Проверить, что запрос без Access не может читать закрытые административные данные или менять GitHub.

### Этап 2 — клиентский API и авторизация
- Удалить хранение GitHub-токена в браузере.
- Перевести клиент на Worker API.
- Добавить состояния загрузки, ошибок, повторного чтения и конфликта версий.
- Сохранить демо-режим только для чтения, если он не раскрывает приватные данные.

### Этап 3 — каркас и дашборд
- Единая навигация, адаптивная компоновка и общие компоненты.
- Состояние публикации, контентные метрики и список проблем.
- Проверить доступность с клавиатуры и мобильный интерфейс.

### Этап 4 — каталог, категории, медиа
- Миграция существующих функций без потери полей и данных.
- Проверка всех операций на тестовой ветке.
- Валидация данных перед записью.

### Этап 5 — редактор нового дизайна
- Карта секций `redesign/index.html`.
- Новый preview bridge с проверкой сообщений.
- Редактирование контента и стилей через типизированную модель.
- Desktop/tablet/mobile preview.

### Этап 6 — SEO, страницы, отзывы, настройки
- Перенос и расширение соответствующих разделов.
- Проверки качества контента и ссылок.

### Этап 7 — публикация, мониторинг, журнал
- Статус CI/deploy.
- Контролируемый запуск публикации.
- Журнал коммитов и безопасный откат.

### Этап 8 — выпуск
- Полный прогон тестов.
- Проверка Cloudflare Access с авторизованной и неавторизованной сессиями.
- Проверка на мобильном устройстве.
- Проверка реальной публикации и отката.
- Обновление README и эксплуатационной инструкции.
- Только после этого считать новую админку готовой.

## 9. Критерии приёмки

- Ни одного GitHub-токена в клиентском коде, хранилище браузера, сетевых ответах и логах.
- Запросы записи без Access авторизации блокируются на Worker.
- Нельзя записать произвольный путь или произвольный GitHub endpoint.
- Некорректный JSON не повреждает исходные данные.
- Конфликт SHA не перезаписывает более новую версию.
- Загрузка неподдерживаемых/слишком больших файлов блокируется сервером.
- Админка редактирует именно актуальный redesign.
- Черновик и опубликованная версия визуально различимы.
- Сайт остаётся доступен и корректно собирается после изменений админки.
- Все показатели панели соответствуют реальным источникам.
- Ошибки API и публикации видны администратору без раскрытия секретов.
- Проверены desktop и mobile сценарии.

## 10. Запреты для реализации

- Не удалять старую админку до завершения миграции и проверки новой.
- Не хранить GitHub PAT в localStorage, sessionStorage, cookie доступной JavaScript или URL.
- Не использовать GitHub token в браузерных запросах.
- Не добавлять базу данных без отдельного обоснования и согласования.
- Не менять публичный дизайн, тексты, каталог и SEO без необходимости для совместимости.
- Не выдавать демо-данные за реальные.
- Не считать запуск сборки успешной публикацией, пока не подтверждён статус deployment.
- Не выполнять force push и не переписывать историю main.
